# The Front Desk API

A small JSON API over Brightline's lobby sign-ins. **This is where the access rules live.**
The pages are a convenience on top; everything below is enforced by the server, whatever the client is.

- Base URL: `http://127.0.0.1:8000` (local only)
- All endpoints are under `/api`. Every response is JSON, including errors.
- Interactive version: `http://127.0.0.1:8000/docs`. It's generated by FastAPI from the same code, and lists the endpoints but contains no data.
- Every example on this page was captured from the running app. Visit ids, names and counts are real values from `data/visits.csv`.

## Authentication

1. `POST /api/auth/signup` creates an account. Only emails on the access list (`data/allowed_users.csv`) are accepted.
2. `POST /api/auth/login` starts an 8-hour session. The session token comes back two ways:
   - as a cookie, `fd_session` (`HttpOnly; SameSite=Lax; Path=/; Max-Age=28800`), which the browser sends automatically
   - in the JSON body as `token`, for curl: send it as `Authorization: Bearer <token>`
3. Every other endpoint needs one of those. If both are sent, the cookie is used.

**What you're allowed to see is decided on every request**, by looking your email up in the access list. It is never
stored in the token, so taking someone off the list (and restarting) ends their access, even with a live session.

Emails are matched the way a person would: case and spaces at either end don't matter
(`" Marcus.Vitale@BRIGHTLINE.example "` is `marcus.vitale@brightline.example`).

Only a hash of each password (scrypt, salted) and of each session token (SHA-256) is stored, in `var/frontdesk.db`.

## Roles and what each sees

| | admin (3 people) | viewer (5 people) | anyone else |
|---|---|---|---|
| Sign up / sign in | ✅ | ✅ | refused (403 at sign-up) |
| Counts, dates, times, visit type, host team, pre-registered | ✅ | ✅ | ❌ 401 |
| Visitor name, email, company | ✅ | **❌ absent from the response** | ❌ 401 |
| Host name, host email | ✅ | **❌ absent from the response** | ❌ 401 |
| The access list (`/api/admin/users`) | ✅ | ❌ 403 | ❌ 401 |

For a viewer, the identity fields aren't hidden, nulled or renamed. **They're never read from the database**, so the
`visitor` and `host` keys don't exist in a viewer's JSON at all (`app/visits.py`, `VIEWER_COLUMNS`). Viewers also can't
filter, search or sort by identity: any query parameter that isn't listed for an endpoint is a 400.

## Errors

Every error is `{"error": "<a message a person can act on>"}` with one of these statuses:

| Status | When | Example message |
|---|---|---|
| 400 | Bad input: dates, visit type, paging, unknown parameter, malformed body | `The end date (2026-07-01) is before the start date (2026-08-01).` |
| 401 | No session, an expired or unknown token, or a wrong login | `Sign in to continue.` / `Email or password is incorrect.` |
| 403 | Signed in but not allowed (viewer → admin endpoint), or sign-up with an email not on the list | `You don't have access to this.` |
| 404 | No such visit, or no such API endpoint | `No visit with id V001996.` / `No such endpoint: GET /api/nope` |
| 409 | Sign-up for an email that already has an account | `An account already exists for this email. Sign in instead.` |
| 500 | Unexpected failure. Never shows details | `Something went wrong on our side. Try again.` |

An unauthenticated call always gets a **JSON 401, never a redirect**.

## Endpoints

| Method and path | Who | What |
|---|---|---|
| `POST /api/auth/signup` | anyone | Create an account (access list only) |
| `POST /api/auth/login` | anyone | Start a session |
| `POST /api/auth/logout` | signed in | End the session |
| `GET /api/me` | signed in | Who am I, and can I see identities |
| `GET /api/visit-types` | signed in | The visit types in the data |
| `GET /api/visits` | signed in | Visits, filtered and paged; fields depend on role |
| `GET /api/visits/:id` | signed in | One visit; fields depend on role |
| `GET /api/stats` | signed in | Counts behind the summary: by weekday, by hour, both, busiest, visit length |
| `GET /api/admin/users` | **admin** | The access list and who has signed up |
| `GET /api/health` | anyone | Liveness check. No data |

### POST /api/auth/signup

Body: `{"email": "<string>", "password": "<string>"}`

Checks run in this order, and the first failure is returned:

| Condition | Status | Message |
|---|---|---|
| email blank | 400 | `Enter your email address.` |
| email not on the access list | 403 | `This email isn't on Brightline's access list. If you think it should be, ask Dana.` |
| password shorter than 8 characters | 400 | `Use a password of at least 8 characters.` |
| account already exists | 409 | `An account already exists for this email. Sign in instead.` |
| body missing or the wrong shape (empty, `[]`, a form) | 400 | `Send a JSON body like {"email": "...", "password": "..."}.` |
| a field missing, e.g. `{"email": "a@b.c"}` | 400 | `password: Field required` |
| a field of the wrong type, e.g. `{"email": 5, …}` | 400 | `email: Input should be a valid string` |
| body isn't valid JSON | 400 | `Request body must be valid JSON.` |
| text that can't be stored (e.g. a lone `\ud800`) | 400 | `email: must be valid text` |

Success, **201**:
```json
{"email": "sam.ferreira@brightline.example", "name": "Sam Ferreira", "role": "viewer"}
```
Sign-up doesn't sign you in. Call login next.

### POST /api/auth/login

Body: `{"email": "<string>", "password": "<string>"}`

Success, **200**. It also sets `Set-Cookie: fd_session=<token>; HttpOnly; Max-Age=28800; Path=/; SameSite=lax`:
```json
{
  "token": "<token>",
  "user": {"email": "sam.ferreira@brightline.example", "name": "Sam Ferreira", "role": "viewer"}
}
```
A wrong password, an unknown email, and an email on the list that hasn't signed up all give the **same** 401
`Email or password is incorrect.`, so a stranger can't tell which it was. Someone removed from the access list can't log in.

### POST /api/auth/logout

Needs a session. Deletes the session the request used and clears the cookie. **204**, empty body.

### GET /api/me

```json
{"email": "sam.ferreira@brightline.example", "name": "Sam Ferreira", "role": "viewer", "can_see_identities": false}
```
```json
{"email": "dana.whitfield@brightline.example", "name": "Dana Whitfield", "role": "admin", "can_see_identities": true}
```

### GET /api/visit-types

The distinct visit types in the loaded data, sorted. It drives the type filter, so nothing is hard-coded.
```json
{"visit_types": ["contractor", "guest", "interview", "vendor"]}
```

### GET /api/visits

| Parameter | Format | Default | Notes |
|---|---|---|---|
| `from` | `YYYY-MM-DD` | none | inclusive |
| `to` | `YYYY-MM-DD` | none | inclusive (`to=2026-09-30` includes 30 Sep) |
| `type` | one of `/api/visit-types` | none | case and spaces ignored (`?type= Interview ` works) |
| `page` | whole number ≥ 1 | 1 | a page past the end is a 400 (when there are results) |
| `page_size` | 1–200 | 50 | |

Ordered newest first. Every filter and count is done by the server.

**Viewer**, `GET /api/visits?type=guest&from=2026-09-30&to=2026-09-30&page_size=1`:
```json
{
  "items": [
    {
      "visit_id": "V001912",
      "date": "2026-09-30",
      "signed_in": "2026-09-30 15:27:00",
      "signed_out": "2026-09-30 16:38:00",
      "duration_min": 71,
      "visit_type": "guest",
      "host_team": "Finance",
      "pre_registered": true
    }
  ],
  "page": 1,
  "page_size": 1,
  "total": 16,
  "total_pages": 16,
  "filters": {"from": "2026-09-30", "to": "2026-09-30", "type": "guest"}
}
```

**Admin**, the same request: each item also has `visitor` and `host`:
```json
{
  "visit_id": "V001912",
  "date": "2026-09-30",
  "signed_in": "2026-09-30 15:27:00",
  "signed_out": "2026-09-30 16:38:00",
  "duration_min": 71,
  "visit_type": "guest",
  "host_team": "Finance",
  "pre_registered": true,
  "visitor": {"name": "Sofia Reyes", "email": "sreyes@oakfieldlega.example", "company": "Oakfield Legal"},
  "host": {"name": "Nadia Ferreira", "email": "nadia.ferreira@brightline.example"}
}
```

A filter that matches nothing is an honest **200** with `"items": []`, `"total": 0`, `"total_pages": 0`.

### GET /api/visits/:id

The same item shape as the list, by role. Any id that isn't a loaded visit gives **404** `No visit with id <id>.`, the
same for viewer and admin. That includes the 58 duplicate sign-ins removed on load (e.g. `V001996`).

### GET /api/stats

Takes `from`, `to`, `type` (same rules as `/api/visits`). Paging parameters are a 400 here. Aggregates only, so it's
**identical for viewer and admin**.

`GET /api/stats?from=2026-08-01&to=2026-08-31&type=interview` (lists shortened with `…`):
```json
{
  "total_visits": 115,
  "range": {"from": "2026-08-01", "to": "2026-08-31"},
  "missing_days": ["2026-08-10", "2026-08-11", "2026-08-12", "2026-08-13"],
  "by_weekday": [
    {"weekday": 0, "name": "Monday", "visits": 22, "operating_days": 4, "avg_per_day": 5.5},
    {"weekday": 1, "name": "Tuesday", "visits": 24, "operating_days": 3, "avg_per_day": 8.0},
    {"weekday": 2, "name": "Wednesday", "visits": 26, "operating_days": 3, "avg_per_day": 8.7},
    {"weekday": 3, "name": "Thursday", "visits": 22, "operating_days": 3, "avg_per_day": 7.3},
    {"weekday": 4, "name": "Friday", "visits": 21, "operating_days": 4, "avg_per_day": 5.2}
  ],
  "by_hour": [{"hour": 9, "visits": 115}, {"hour": 10, "visits": 0}, "…"],
  "by_weekday_hour": [{"weekday": 0, "hour": 9, "visits": 22, "avg_per_day": 5.5}, "…"],

  "visit_length": {"median_min": 93, "measured_visits": 67, "total_visits": 115}
```

### GET /api/admin/users

**Admin only.** A viewer gets **403** `You don't have access to this.`, whatever the page shows. Admins are listed first, then by name:

## Field glossary

| Field | Meaning |
|---|---|
| `visit_id` | The iPad's id for the visit |
| `date` | The day of the visit (from the sign-in time) |
| `signed_in`, `signed_out` | `YYYY-MM-DD HH:MM:SS`, office local time. `signed_out` is `null` when the guest didn't sign out (about 45% of visits) |
| `duration_min` | Minutes between sign-in and sign-out; `null` without a sign-out |
| `visit_type` | `contractor`, `guest`, `interview` or `vendor` (whatever the data contains) |
| `host_team` | The host's team on that visit |
| `pre_registered` | Whether the visit was registered in advance |
| `visitor`, `host` | **Admins only.** The keys are absent for viewers |

## Filters

- Accepted parameters are exactly the ones listed for each endpoint. **Anything else → 400**
  `Unknown filter: <name>. Use from, to, type[, page, page_size].` This is deliberate: there is no way to filter, search
  or sort by a visitor's identity.
- Giving a parameter twice → 400 `Give <name> only once.`
- An empty value (`?type=`) means "no filter". An empty `page=` is a 400.

| Bad input | Message |
|---|---|
| `from=14/08/2026` | `from must be a date written as YYYY-MM-DD.` |
| `to=2026-02-30` | `to must be a date written as YYYY-MM-DD.` |
| `from=2026-08-31&to=2026-08-01` | `The end date (2026-08-01) is before the start date (2026-08-31).` |
| `type=intervew` | `Unknown visit type 'intervew'. Choose one of: contractor, guest, interview, vendor.` |
| `page=0`, `page=two`, a 10+ digit page | `page must be a whole number from 1.` |
| `page_size=500` | `page_size must be a whole number from 1 to 200.` |
| `page=999` (with results) | `Page 999 doesn't exist. There are 40 pages.` |

## How the stats are calculated

- **Duplicates removed on load.** If the same visitor signs in with the same host on the same day within 2 minutes, and
  the second sign-in has no sign-out, it's the iPad double-recording one tap. 58 rows are dropped, leaving 1,953 visits.
- **Operating days** are the dates in the range with at least one sign-in of any type. Weekday averages divide by these,
  so a day with no data (like the 10–13 August outage) doesn't count as a quiet day. The range also has one more Wednesday
  than other weekdays, which a plain total would reward.
- **Busiest** lists every weekday (by average per operating day) or hour (by count) within 5% of the top value. Ties are
  shown, not hidden.
- **`by_hour`** covers every hour from the earliest to the latest sign-in in the whole dataset, so empty hours (12 pm) show as 0.
- **`missing_days`** are weekdays inside the data's span with no sign-ins at all, detected on load and not hard-coded.
- **`visit_length.median_min`** is the median over visits with a sign-out only. `measured_visits` says how many that is.
